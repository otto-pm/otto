# Otto: AI-Powered Project Management

![Otto Logo](https://raw.githubusercontent.com/otto-pm/otto/main/docs/assets/otto-logo.png) <!-- Placeholder for a logo, assuming one exists or will be created -->

An AI-Powered Project Management Solution designed to revolutionize software development workflows. Otto leverages advanced AI to automate documentation, enhance code understanding, streamline repository ingestion, and facilitate seamless collaboration.

## 🚀 Features

Otto is built to empower development teams with intelligent automation, focusing on reducing manual overhead and improving code quality and accessibility.

*   **Intelligent Documentation Generation:**
    *   Automatically generate comprehensive API documentation, user guides, technical specifications, and `README.md` files directly from your codebase.
    *   Supports various documentation types (`api`, `user_guide`, `technical`, `readme`).
    *   Leverages advanced RAG (Retrieval-Augmented Generation) to ensure documentation is accurate and contextually relevant to your code.
*   **Deep Codebase Understanding:**
    *   Processes and chunks code repositories to build a sophisticated understanding of project structure, classes, methods, functions, and their interrelationships.
    *   Extracts detailed context, including imports, class methods, and their types (static, class methods, properties).
*   **Seamless GitHub Integration:**
    *   Push generated documentation directly to your GitHub repositories.
    *   Automatically create new branches and open pull requests for review, ensuring version control and team collaboration.
    *   Verifies user and repository access permissions for secure operations.
*   **Local File Management:**
    *   Option to save all generated content and processed data locally to a designated output directory for easy review, debugging, and offline access.
*   **Scalable Backend API:**
    *   A robust FastAPI-based backend provides a powerful and extensible API for all AI services, repository management, and user interactions.
*   **Multi-language Support:**
    *   Designed to handle multiple programming languages, with explicit support for Python and TypeScript code analysis and documentation generation.

## 🛠️ Installation

To get Otto up and running, follow these steps. We recommend using Docker Compose for the easiest setup.

### Prerequisites

*   Python 3.9+
*   Node.js (LTS recommended, for potential TypeScript frontend/utility services)
*   Git
*   Docker & Docker Compose (recommended for local development and deployment)
*   GitHub Personal Access Token (with `repo` scope for pushing documentation)
*   Google Cloud Project (if utilizing GCP services like Storage)
*   API Key for your chosen Large Language Model (e.g., OpenAI, Anthropic)

### 1. Clone the Repository

```bash
git clone https://github.com/otto-pm/otto.git
cd otto
```

### 2. Environment Configuration

Create `.env` files in the `backend/app` and `ingest-service` directories based on the provided examples (or create them manually).

**`backend/app/.env` (Example):**

```env
# GitHub Integration
GITHUB_APP_ID=YOUR_GITHUB_APP_ID
GITHUB_PRIVATE_KEY_PATH=/path/to/your/github-app-private-key.pem
GITHUB_WEBHOOK_SECRET=YOUR_GITHUB_WEBHOOK_SECRET

# Google Cloud (if applicable)
GCP_PROJECT_ID=your-gcp-project-id
BUCKET_RAW=otto-raw-data
BUCKET_PROCESSED=otto-processed-data

# LLM Configuration
OPENAI_API_KEY=sk-YOUR_OPENAI_API_KEY
ANTHROPIC_API_KEY=sk-YOUR_ANTHROPIC_API_KEY
LLM_PROVIDER=openai # or anthropic, etc.

# FastAPI Settings
APP_SECRET_KEY=YOUR_APP_SECRET_KEY_FOR_JWT
DATABASE_URL=sqlite:///./sql_app.db # Or your PostgreSQL/MySQL URL
```

**`ingest-service/.env` (Example):**

```env
# Google Cloud (if applicable)
GCP_PROJECT_ID=your-gcp-project-id
BUCKET_RAW=otto-raw-data
BUCKET_PROCESSED=otto-processed-data

# LLM Configuration
OPENAI_API_KEY=sk-YOUR_OPENAI_API_KEY
ANTHROPIC_API_KEY=sk-YOUR_ANTHROPIC_API_KEY
LLM_PROVIDER=openai # or anthropic, etc.

# GitHub Token for service-level operations (if different from user's)
SERVICE_GITHUB_TOKEN=ghp_YOUR_SERVICE_GITHUB_TOKEN

# Output directory for local saves
OUTPUT_DIR=./output
```

### 3. Install Dependencies (Manual Setup)

If not using Docker, you'll need to install dependencies for each service.

```bash
# For the backend service
cd backend/app
pip install -r requirements.txt

# For the ingest service
cd ../../ingest-service
pip install -r requirements.txt

# For any TypeScript-based frontend or utilities (if applicable)
# cd ../frontend # Assuming a frontend directory
# npm install
```

### 4. Run with Docker Compose (Recommended)

For a streamlined setup, use Docker Compose. Ensure Docker is running on your system.

```bash
# From the root of the repository
docker-compose up --build
```

This will build and start all necessary services (backend, ingest-service, etc.).

### 5. Run Services (Manual Setup)

If you're not using Docker Compose, you'll need to start each service manually.

```bash
# Start the FastAPI backend
cd backend/app
uvicorn main:app --host 0.0.0.0 --port 8000 --reload

# Start the ingest service (if it runs as a separate process or worker)
cd ../../ingest-service
python -m src.main # Or whatever the entry point is for your ingest service
```

## 💡 Usage

Once your Otto services are running, you can interact with them via the API. The primary use case demonstrated here is generating documentation.

### Generating Documentation via API

You can trigger documentation generation by sending a `POST` request to the `/docs/generate` endpoint.

**Example Request (using `curl`):**

```bash
curl -X POST "http://localhost:8000/api/v1/docs/generate" \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer YOUR_USER_AUTH_TOKEN" \
     -d '{
           "target": "generate_documentation",
           "repo_full_name": "otto-pm/otto",
           "doc_type": "api",
           "stream": false,
           "push_to_github": true,
           "save_local": true
         }'
```

**Explanation of Request Body:**

*   `target`: The specific code entity you want to document (e.g., a function name, class name, or even a file path).
*   `repo_full_name`: The full name of the GitHub repository (e.g., `owner/repo`).
*   `doc_type`: The type of documentation to generate. Valid options include:
    *   `api`: For API reference documentation.
    *   `user_guide`: For user-facing guides.
    *   `technical`: For internal technical specifications.
    *   `readme`: To generate or update the `README.md` file.
*   `stream`: If `true`, the API might stream partial documentation results as they are generated (if implemented).
*   `push_to_github`: If `true`, the generated documentation will be pushed to the specified GitHub repository, potentially creating a new branch and a pull request.
*   `save_local`: If `true`, the generated documentation will also be saved to the local `output` directory configured in the `ingest-service`.
